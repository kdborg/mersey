# Servo integration (Stage B)

**The fork exists.** `<script type="text/mersey">` in a page is compiled and
executed by the Mersey engine inside Servo — no SpiderMonkey for the Mersey
code, no WASM in the stack — through the same C ABI that `native/host_demo.c`
and `crates/mersey_capi/tests/abi.rs` drive in this repository, and that the
Gecko and Chromium forks drive too. One boundary, four hosts.

Servo is Rust, so the integration is lighter than the C++ forks: the engine is
a **crate** in Servo's build (one `std`, one link — like the Gecko fork's
`gkrust`, unlike Chromium's prebuilt `.so`), and the web bridge is **reflective
Rust→SpiderMonkey**: the host table's `web_*` hooks call the tested
`web/mersey-bridge.js` (five reflective ops — global/get/set/call/construct —
over a handle table) through `JS_CallFunctionName`, exactly as the WASM polyfill
does. That is the honest bootstrap; the direct-C++ typed fast paths the other
forks grew are not built here yet.

The Servo tree is not *in* this repo (a checkout is large). It lives beside it:

```
~/servo-src   nightly 2026-07-15 src-vendored, built for aarch64-linux-gnu
  components/script/mersey/         the engine module + reflective bridge
  components/script/{lib.rs,Cargo.toml,dom/html/htmlscriptelement.rs}  the hook
  vendor/                           the engine's crates (interp + Cranelift)
```

## What landed

| | |
|---|---|
| `components/script/mersey/mod.rs` | one engine context per script thread (a raw-pointer thread-local — re-entrant by the ABI's thread rule, like `mersey_capi`'s own `MsyContext`). The host table is wired to stdout (`print`), a monotonic clock (`time_ms`), and the reflective web bridge. Every fast-path pointer is `NULL`, so the engine falls back to the reflective ops — same results, verified by matching workload checksums. A JS callback re-enters the engine through `msy_context_invoke_args` (the injected `__merseyInvoke`). |
| `components/script/mersey/bridge.js` | `web/mersey-bridge.js` with the ES import stripped and a `globalThis.__merseyBridge = makeBridge(...)` epilogue. Generated by `refresh-bridge.sh`; do not edit by hand. |
| `components/script/dom/html/htmlscriptelement.rs` | `ScriptType::Mersey`. An **inline** `text/mersey` script runs at prepare time via `crate::mersey::run_mersey_script`, bypassing the classic/module machinery. |
| `components/script/Cargo.toml` | the `mersey_capi` path dependency, default features — the **Cranelift Tier-1 JIT is on**. |
| `vendor/` | the engine's dependency tree, vendored for Servo's offline build: the interpreter's few crates and Cranelift's ~30 (`vendor-deps.sh`). |

## Building it

Prerequisites: an `~/servo-src` checkout (the nightly `*-src-vendored.tar.gz`
extracted), `uv` on `PATH`, and Servo's system build deps (`./mach bootstrap`
or the apt list in `python/servo/platform/linux_packages/apt/`). The engine's
crates must be in the local cargo cache first, which building the engine here
does:

```bash
cargo build --release -p mersey_capi        # populate ~/.cargo cache (jit on)

servo/apply.sh    ~/servo-src               # install the module + the hook
servo/vendor-deps.sh ~/servo-src            # vendor the engine's crates into vendor/

cd ~/servo-src
PATH="$HOME/.local/bin:$PATH" ./mach build --release   # -> target/release/servoshell
```

Then measure, from this repo:

```bash
node bench/web/run-native-servo.mjs         # -> bench/web/results.native.servo.json
```

## Notes

- **aarch64, from source.** Servo publishes no aarch64 desktop nightly (its
  prebuilt is x86-64 only), so the fork is built from the vendored source. None
  of the Chromium fork's arm64 toolchain archaeology applies — Servo's build is
  ordinary `cargo` once the system libs are present.
- **The JIT is vendored.** Enabling `mersey_capi`'s `jit` feature pulls
  Cranelift; `vendor-deps.sh` copies it (and the version-specific and
  target-specific crates `cargo tree` misses) into `vendor/`. Compute runs the
  Tier-1 JIT; the JIT also compiles the web loops once warm.
- **http, not `file://`.** The native harness serves over http because Servo
  exposes `localStorage` only on an http origin — which also matches the stock
  runs. The other web workloads are origin-independent.
- **Reflective bridge is the remaining gap.** Servo's web workloads sit ~2–5×
  the Gecko fork purely because every web call crosses as tagged JSON through
  SpiderMonkey. Direct-Rust fast paths against Servo's DOM bindings are the
  natural next lever.
