Mersey · engine benchmarks

Plain JS, WASM polyfill, and native Mersey — compute and the web platform

The same programs written once in JavaScript and once in Mersey, run four ways in two browsers — plain JS, the WASM-interpreter polyfill, the transpiled-JS polyfill (with its Mersey→WASM compute tier), and the native fork — over a compute kernel and six web-platform workloads. Identical work, verified by matching checksums; the only variable is what executes the code.

Compute — where the JIT lands

A hot integer kernel (40M iterations, no allocation, no web calls) — the case the Tier-1 JIT compiles to native code. This is a different workload from the six below: those are host-bound (dominated by web-API calls); this one is compute-bound. Log scale, self-timed, lower is faster.

plain JS (JIT) native — Mersey in the fork (Cranelift JIT) polyfill — transpiled JS + Mersey→WASM tier polyfill — WASM interpreter

Wiring Cranelift into the fork puts native Mersey at or ahead of hand-written JS on the compute kernel (104 vs 111 ms) and ~150–800× ahead of the WASM polyfill, which has no JIT. The JIT gained two things this round: std:math intrinsics (sqrt/min/max/… lower to machine instructions — mathk fell from 1913 ms interpreted to 36 ms, ~53×), and a leaf-function inliner (a small helper's body is expanded at the call site, bit-identical to a real call — the calls kernel, 20M nested calls, fell 68→25 ms, 2.7×). It also compiles the web loops below (see the web note), so its reach is no longer compute-only.

The new polyfill: Mersey transpiled to JavaScript

The polyfill grew a second execution mode: the same front end (same checker, same diagnostics) now emits JavaScript at load time, and the browser's own JIT runs it — the WASM interpreter stays as the conformance vehicle. Gated by the full runtime conformance suite (31/31 goldens pass, matching the engine byte for byte) and the same workload checksums. Module graphs link as real ES modules (the engine's Mersey-written std: modules transpile into the graph too), dynamic import() works, capabilities stay enforced (data-allow), and a page whose CSP forbids blob: scripts falls back to the WASM engine automatically. Browser suites: platform 21/21, harness 44/44, modules 4/4, browser 46/46, lazy/random/pixels/security/sw all green — remaining gaps are custom-element attach semantics and Mersey stack traces (source maps). On web-platform workloads the transpiled polyfill is at hand-written-JS speed (within noise; sometimes ahead), 10–60× the WASM interpreter. Compute got its own compiler: the polyfill's Mersey→WASM tier compiles typed numeric functions (the same subset the native Cranelift JIT accepts) to a real WebAssembly module — int32/int64 as machine types, no |0 shims — and the JS backend binds the exports. Chromium compute: 92 ms, ahead of hand-written JS (94) and ~210× the WASM interpreter; Firefox: 150 ms (measured in a full Firefox build — Playwright's bundled Firefox runs WASM without its optimizing tier and reports 657 ms, a harness artifact, checksums identical). Gated by the same 31/31 conformance goldens with the tier active. This is what ships as the Stage-A polyfill; the engine-in-browser remains Stage B.

The compiler then got an optimization round — a leaf-function inliner (the wins a JS JIT's inliner gets for free, done at compile time for wasm) and std:math intrinsics (sqrt/abs/floor/min/max lower to single f64 opcodes instead of host calls). Cheap-op loops — native matches or beats JS. Where the per-iteration host op is light and native's direct-C++ path is leaner than V8's binding, removing interpreter dispatch and the per-call intern lets native undercut the JS engine: interleaved A/B shows crypto BEATS JS (native/JS 0.88× median — getRandomValues fills a C++ buffer with no JS typed-array), and canvas matches JS (~1.0–1.17×).
Heavy shared-op loops — parity is the floor. storage (localStorage backend), url (Gecko's URL parser) and dom (createElement/appendChild build real layout nodes) are dominated by C++ work both engines call identically. Their loops compile correctly now, but that removes only the ~180 ns of dispatch on top of a ~1–2 µs shared op, so they stay ~2×. That gap is the shared platform work, not the engine.
On compute, native beats JS (103 vs 111 ms) — no bindings, no shared backend — and the JIT's std:math intrinsics took mathk from 1913 ms (interpreted) to 36 ms (~53×).

Making native faster: two separate levers

Compute and web-platform code have different bottlenecks, so they got different work. Compute got the JIT: Cranelift is now compiled into the fork (24 vendored crates, two latent version-unification bugs in Gecko's own hashbrown/bitflags shims fixed along the way), and it delivers the 65× above. Web-platform code is host-bound — the JIT refuses it (it allocates and calls the host every iteration) — so the bridge got faster instead, in seven steps: a member name crosses the ABI once as an integer (interning); scalar arguments cross without JSON (setItem(k,v), fillRect(…)); Web Storage skips JS entirely via Gecko's C++ Storage; replies come back typed, not as JSON; and finally the engine adopted UTF-16 (WTF-16) strings — the same encoding as Gecko and V8. So strings now cross with no conversion at all: an argument is a zero-copy view of the engine's own buffer, a reply is a plain copy of the host's code units. No UTF-8 intermediary, no JSON, no per-character re-encoding — the whole string tax is gone. Then two more: object handles ride the fast path (a ref crosses as a number plus a mask bit, so appendChild(el) and getRandomValues(buf) stopped falling back to reflective JSON), and hot DOM/canvas operations are now direct C++ on unwrapped natives: a handle is unwrapped once to its Gecko object, then fillRect / appendChild / textContent never enter JS at all (canvas 21→15 ms). Separately, JSON.stringify/parse on pure data is now served by the engine's own writer — no bridge call, no double serialization (json 88→28 ms) — and the interpreter fused template strings into a single-allocation join (1.4× on interpolation-heavy loops). The latest step closes the last big gap: object creation stays in C++ too. new URL(s), createElement and new Uint8Array(n) build the Gecko object (or a byte buffer) directly and hand back a negative handle that never enters JS — every subsequent read (url.pathname, getRandomValues(buf)) dispatches on it in C++. A JS reflector is materialized once, lazily, only if such an object ever escapes to an API the fast paths don't cover. This is what URL and DOM were waiting on — their objects used to be born in JS and drag every operation back there (url 104→54, dom 31→15, crypto 32→16 ms). These C++-created objects live in a freelist-indexed slot vector — creation, every property read, and release are O(1) with no per-object allocation, which matters when a frame creates and drops thousands of them (storage, which never left C++, also settled to 68 ms). A correctness note from the same pass: once such a buffer escapes to JS its bytes become a separate copy, so getRandomValues on an escaped buffer now fills the JS array rather than diverging from it. (These native numbers are measured with browser telemetry/region/search services disabled, so background CPU no longer steals from the timed loop — the same quiet footing the stock browsers already had.) How to read this honestly

  • The bridge fast paths help where the hot calls are scalars. URL (1.36×) and canvas (1.33×) gain most; JSON (0.95×, within noise) gains nothing because its argument is an object that still needs serializing. This is the win available without abandoning the universal reflective bridge.
  • Direct C++ shifts the bottleneck rather than removing it. Web Storage now bypasses JS entirely, yet it is still ~4× slower than the browser's own localStorage (which calls the same C++). Bypassing JS only bought ~1.15× over the interned bridge — because the remaining cost is no longer the crossing, it is the Tier-0 interpreter loop plus per-call string marshalling and reply parsing. Which means, for a bridge that is now fast, the JIT finally becomes the lever.
  • The JIT is done, and it is huge — for compute. Cranelift in the fork makes an arithmetic kernel 65× the interpreter and competitive with JS. It stays out of the web-platform loops by design (they allocate and call the host every iteration), so the two levers don't overlap: JIT for compute, bridge for web APIs.
  • The memory baselines differ on purpose. The polyfill pays a per-page engine tax of ~40–52 MB (WASM module + heap); the native engine adds none, because it ships inside the browser — and native's footprint is the lowest of the three.
  • Native is Firefox-only so far. The Chromium fork needs the same bridge port before it can be measured.
