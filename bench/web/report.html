Mersey · engine benchmarks

Plain JS, WASM polyfill, and native Mersey — compute and the web platform

The same programs written once in JavaScript and once in Mersey, run four ways across three browsers — plain JS, the WASM-interpreter polyfill, the transpiled-JS polyfill (with its Mersey→WASM compute tier), and the native fork — over a compute kernel and twenty-five web-platform workloads (Web Storage, JSON, URL, Web Crypto, Canvas 2D, DOM mutation, DOM events, CSSOM, selector queries, TextEncoder/Decoder, timers, fetch, WebSockets, IndexedDB, Streams, XMLHttpRequest, Web Workers, Compression Streams, Broadcast Channel, Geometry, File API, Server-sent events, URL Pattern, Web Locks, and Channel Messaging). The three stock browsers are Chromium (V8), Firefox (SpiderMonkey), and Servo (SpiderMonkey, its own web platform). Identical work, verified by matching checksums; the only variable is what executes the code.

Every native number here is the Tier-1 JIT, and the JIT is held to the interpreter's answer: a differential fuzzer runs generated programs — numeric, object, and string — on the tree-walker, the bytecode VM, and the JIT, and fails on any disagreement. The speed below is compiled speed that produces the same result as the reference engine, thousands of programs over.

Compute — where the JIT lands

A hot integer kernel (40M iterations, no allocation, no web calls) — the case the Tier-1 JIT compiles to native code. This is a different workload from the twenty-five below: those are host-bound (dominated by web-API calls); this one is compute-bound. Log scale, self-timed, lower is faster.

Wiring Cranelift into the fork puts native Mersey at or ahead of hand-written JS on the compute kernel (104 vs 111 ms) and ~150–800× ahead of the WASM polyfill, which has no JIT. The JIT gained two things this round: std:math intrinsics (sqrt/min/max/… lower to machine instructions — mathk fell from 1913 ms interpreted to 36 ms, ~53×), and a leaf-function inliner (a small helper's body is expanded at the call site, bit-identical to a real call — the calls kernel, 20M nested calls, fell 68→25 ms, 2.7×). It also compiles the web loops below (see the web note), so its reach is no longer compute-only.

The new polyfill: Mersey transpiled to JavaScript

The polyfill grew a second execution mode: the same front end (same checker, same diagnostics) now emits JavaScript at load time, and the browser's own JIT runs it — the WASM interpreter stays as the conformance vehicle. Gated by the full runtime conformance suite (31/31 goldens pass, matching the engine byte for byte) and the same workload checksums. Module graphs link as real ES modules (the engine's Mersey-written std: modules transpile into the graph too), dynamic import() works, capabilities stay enforced (data-allow), and a page whose CSP forbids blob: scripts falls back to the WASM engine automatically. Browser suites: platform 21/21, harness 44/44, modules 4/4, browser 46/46, lazy/random/pixels/security/sw all green — remaining gaps are custom-element attach semantics and Mersey stack traces (source maps). On web-platform workloads the transpiled polyfill is at hand-written-JS speed (within noise; sometimes ahead), 10–60× the WASM interpreter. Compute got its own compiler: the polyfill's Mersey→WASM tier compiles typed numeric functions (the same subset the native Cranelift JIT accepts) to a real WebAssembly module — int32/int64 as machine types, no |0 shims — and the JS backend binds the exports. Chromium compute: 92 ms, ahead of hand-written JS (94) and ~210× the WASM interpreter; Firefox: 150 ms (measured in a full Firefox build — Playwright's bundled Firefox runs WASM without its optimizing tier and reports 657 ms, a harness artifact, checksums identical). Gated by the same 31/31 conformance goldens with the tier active. This is what ships as the Stage-A polyfill; the engine-in-browser remains Stage B.

The compiler then got an optimization round — a leaf-function inliner (the wins a JS JIT's inliner gets for free, done at compile time for wasm) and std:math intrinsics (sqrt/abs/floor/min/max lower to single f64 opcodes instead of host calls). Pure-engine loops — native beats JS. Where the work is the engine's own — no shared C++ backend — removing interpreter dispatch lets native undercut the JS engine: json beats Firefox JS (3.2 vs 3.6 ms, the JSON.stringify→template fusion below) and canvas matches it (4.4 vs 4.6 ms). crypto is a wash — an interleaved same-build A/B has put native slightly ahead (getRandomValues fills a C++ buffer with no JS typed-array), but the cross-run table has Firefox JS a shade faster (8.1 vs 10.4 ms); it is close enough that which side wins depends on the run.
Heavy shared-op loops — parity is the floor. storage (localStorage backend), url (Gecko's URL parser) and dom (createElement/appendChild build real layout nodes) are dominated by C++ work both engines call identically. The last two now compile the whole loop: the JIT learned new URL(s) and string component reads (url.pathname/search), and that a handle cast (el as HTMLElement) is a no-op — the ops that used to bail the function to the interpreter. Removing that dispatch took url 51→41 and dom 14→13 ms, but it is only ~180 ns saved on top of a ~1–2 µs shared op, so they stay ~1.5–2×. That remaining gap is the shared platform work, not the engine.
On compute, native beats JS (103 vs 111 ms) — no bindings, no shared backend — and the JIT's std:math intrinsics took mathk from 1913 ms (interpreted) to 36 ms (~53×).

Making native faster: two separate levers

Compute and web-platform code have different bottlenecks, so they got different work. Compute got the JIT: Cranelift is now compiled into the fork (24 vendored crates, two latent version-unification bugs in Gecko's own hashbrown/bitflags shims fixed along the way), and it delivers the 65× above. Web-platform code is host-bound — the JIT refuses it (it allocates and calls the host every iteration) — so the bridge got faster instead, in seven steps: a member name crosses the ABI once as an integer (interning); scalar arguments cross without JSON (setItem(k,v), fillRect(…)); Web Storage skips JS entirely via Gecko's C++ Storage; replies come back typed, not as JSON; and finally the engine adopted UTF-16 (WTF-16) strings — the same encoding as Gecko and V8. So strings now cross with no conversion at all: an argument is a zero-copy view of the engine's own buffer, a reply is a plain copy of the host's code units. No UTF-8 intermediary, no JSON, no per-character re-encoding — the whole string tax is gone. Then two more: object handles ride the fast path (a ref crosses as a number plus a mask bit, so appendChild(el) and getRandomValues(buf) stopped falling back to reflective JSON), and hot DOM/canvas operations are now direct C++ on unwrapped natives: a handle is unwrapped once to its Gecko object, then fillRect / appendChild / textContent never enter JS at all (canvas 21→15 ms). Separately, JSON.stringify/parse on pure data is now served by the engine's own writer — no bridge call, no double serialization (json 88→28 ms) — and the interpreter fused template strings into a single-allocation join (1.4× on interpolation-heavy loops). The last json step goes further: the compiler now fuses JSON.stringify({literal}) straight into template bytecode at compile time — the constant keys and scalar values are baked into string fragments (byte-for-byte the same escaping the writer uses), and integer fields become dynamic parts — so the object literal is never built and the serializer never runs. What was an interpreted record-allocate-then-serialize loop is now a Tier-1 JIT-compiled string join, and json drops 24→3.3 ms — under Firefox's own JSON.stringify (3.6 ms). The fusion is guarded by the type checker (only the real JSON global, only bakeable-constant or int32/int64 fields), so a shadowed JSON or a dynamic-string field falls back to the writer unchanged. The latest step closes the last big gap: object creation stays in C++ too. new URL(s), createElement and new Uint8Array(n) build the Gecko object (or a byte buffer) directly and hand back a negative handle that never enters JS — every subsequent read (url.pathname, getRandomValues(buf)) dispatches on it in C++. A JS reflector is materialized once, lazily, only if such an object ever escapes to an API the fast paths don't cover. This is what URL and DOM were waiting on — their objects used to be born in JS and drag every operation back there (url 104→54, dom 31→15, crypto 32→16 ms). These C++-created objects live in a freelist-indexed slot vector — creation, every property read, and release are O(1) with no per-object allocation, which matters when a frame creates and drops thousands of them (storage, which never left C++, also settled to 68 ms). A correctness note from the same pass: once such a buffer escapes to JS its bytes become a separate copy, so getRandomValues on an escaped buffer now fills the JS array rather than diverging from it. (These native numbers are measured with browser telemetry/region/search services disabled, so background CPU no longer steals from the timed loop — the same quiet footing the stock browsers already had.) How to read this honestly

  • Native and stock JS aren't the same build — the same-host panel is the fair read. The native fork is a developer build (dcheck_always_on + libc++ extensive hardening, not is_official_build) served over file://; the JS/poly/tjs bars use stock release browsers over http, which run the identical work 4–22× faster. So the cross-way web-platform bars understate native. Measured in the same fork over file://, native leads five of the six web workloads (url ~8×, json/crypto/storage ~2–3×, canvas ~1.6×) and runs even with JS on dom (1.1×) and the compute kernel. Remaining asymmetry: the engine .so is release while the fork's V8 is DCHECK'd, so the exact multiples are soft.
  • Storage's cost is the platform, not the bridge. Caching the resolved StorageArea took it 283→218 ms; swapping the real CachedStorageArea for an in-process map (same marshalling) drops it to ~38 ms — faster than the Firefox fork — so the bridge and engine are lean. The rest is Chromium's file:// localStorage backend (a mojo Put per setItem), slow for everyone: plain JS over the same origin takes ~500 ms, so native already beats it 2×. A platform floor, not a JIT lever.
  • The bridge fast paths help where the hot calls are scalars. URL (1.36×) and canvas (1.33×) gain most; JSON (0.95×, within noise) gains nothing because its argument is an object that still needs serializing. This is the win available without abandoning the universal reflective bridge.
  • The JIT is done, and it is huge — for compute. Cranelift in the fork makes an arithmetic kernel 65× the interpreter and competitive with JS. It stays out of the web-platform loops by design (they allocate and call the host every iteration), so the two levers don't overlap: JIT for compute, bridge for web APIs.
  • The memory baselines differ on purpose. The polyfill pays a per-page engine tax of ~40–52 MB (WASM module + heap); the native engine adds none, because it ships inside the browser — and native's footprint is the lowest of the three.
  • Chromium native: engine + a growing web bridge. The Chromium fork hosts the engine (it edges the Gecko fork on calls/compute/fcompute/mathk, runs json via the fusion), and its Blink script runner now grows a direct-C++ web bridge: url (via KURL), dom (createElement/appendChild/ textContent on real Blink nodes), crypto (a native byte buffer + getRandomValues), and canvas (getContext/fillRect) run — and on the interned typed fast paths (a name crosses once as an id, then scalars cross typed with no JSON) url/dom/crypto/canvas land at 66 / 25 / 16 / 11 ms, ~1.3–2.6× the Gecko fork and checksums verified. storage and canvas live in Blink's modules/ layer, which core can't depend on, so both go through a core→modules hook (core declares a function-pointer table; ModulesInitializer fills it). All six web workloads now run in both forks; storage (218 ms, down from 283 once the hook cached the resolved StorageArea) reads as the outlier but isn't a Mersey cost. Swapping the real CachedStorageArea for an in-process map (same bridge marshalling) drops it to ~38 ms — faster than the Firefox fork — so the bridge and engine are lean; the rest is Chromium's file:// localStorage backend (a mojo Put per setItem). That backend is slow for everyone: plain JS over the same file:// origin in this fork takes ~500 ms, so native already beats it 2–3×. The JS/poly bars measure an http origin (Playwright, stock Chromium), where localStorage is much cheaper — not a like-for-like backend for the file:// native run. Harness: run-native-chromium.mjs; data: results.native.chromium.json.
  • Servo is the third browser — stock and native. Servo (2026-07-15 nightly, built from source on aarch64) runs the js, polyfill, and transpiled-JS legs like Chromium and Firefox; all six web workloads plus the compute kernel run with matching checksums. Its JS engine is SpiderMonkey, so plain-JS numbers track Firefox closely (compute 108 vs 111 ms). Servo's WASM has no optimizing tier, so the polyfill interpreter numbers are in the same class as the other browsers' (compute ~19 s), and its stock localStorage writes synchronously, so storage is slow for all three impls (~2–3.6 s) — a platform cost, not a Mersey one.
  • Servo native: the engine embedded, with the Cranelift JIT. The Servo fork now hosts the engine (a new components/script/mersey, hooking <script type="text/mersey">), so Servo has a native column like the other two forks — all six web workloads run with matching checksums (canvas 19, crypto 18, dom 32, json 1, url 36, storage 1953 ms). Cranelift is vendored into Servo too (the ~30 crates added to vendor/), so the engine runs the Tier-1 JIT: the compute kernel is ~95 ms — a real JIT number, the fastest of the three native forks and ahead of Servo's own JS (108), down from 6.3 s interpreted. The JIT also compiles the web loops after they warm. The interned + scalar and now the wide-string bridge fast paths are wired: a member name crosses once as an integer id, and get/set/call/new cross with no JSON and, on the wide path, no encoding conversion — object arguments (appendChild(el), getRandomValues(buf)) stay off the JSON path via a refs bitmask. Wiring the wide-string tier (the web_*_u16 hooks) cut crypto 39→18, url 67→36, canvas 27→18, dom 35→32 — url now edges out the Gecko fork — with checksums unchanged. What remains is the direct-DOM tier the C++ forks built (web_bind → the DOM method with no JS at all), the last lever to the Gecko fork. The Servo fork runs over an http origin (like the stock runs) because Servo exposes localStorage only there, not over file://; storage's ~2 s is that slow backend, not the bridge (the wide path did not move it). Harness: run-servo.mjs / run-native-servo.mjs; data: results.servo.json / results.native.servo.json.
  • Ladybird native: the newest fork, engine + Cranelift JIT. Ladybird (LibWeb + LibJS, built from source via test-web — it ships no --headless binary) now hosts the engine through a C++ module (Libraries/LibWeb/Mersey), the fifth host of the one C ABI. All six web workloads + compute run with matching checksums. Compute is ~93 ms — the fastest of the three native forks (pure JIT, no bridge). The reflective bridge is C++→LibJS (UTF-16 end to end), with the interned and wide-string fast paths wired — the same lever as Servo, which cut crypto 117→50, url 220→124, canvas 56→38, dom 94→68. The typed-binding tier (web_bind) is wired too: the JIT-compiled canvas loop calls the C++ CanvasRenderingContext2D::fill_rect directly — no JS, no marshalling — dropping canvas 38→10 ms, on par with Chromium. The direct-DOM tier then reached the rest of the web workloads: each hot method is classified when its name is interned, and the wide-path hook unwraps the receiver (and object args) to their C++ types and calls the method directly — getRandomValues (crypto 117→26), new URL+pathname/search (url 220→55, now ahead of the Chromium fork), and createElement+textContent+ appendChild (dom 94→29, ahead of Servo). Objects the host creates (URL, elements) are registered once and their C++ pointer cached, so the follow-up reads never cross. storage (~9.8 s) is the lone holdout — bound by Ladybird's own localStorage, not the crossing. Harness: run-native-ladybird.mjs; data: results.native.ladybird.json. The stock leg (js/poly/tjs) is not collected yet.
  • Why storage is the one workload no fork tier moves. It is the cleanest evidence that the engine and bridge are not the cost: wiring the wide-string path (no JSON) changed it by <1% in both Servo and Ladybird. The cost is each browser's localStorage backend, which must persist and sync across contexts, so it is synchronous cross-process IPC. Ladybird does three IPC round-trips per iteration — page_did_set_storage_item, a storage-event broadcast, and page_did_request_storage_item — for ~10 s; Servo proxies to a storage thread (~2 s); Chromium's StorageArea caches, so it is far faster (~218 ms). A Mersey fork cannot close this — bypassing the IPC would break persistence and storage events. It is a browser-storage-architecture cost, identical for the browser's own JS, and the gap between the three is theirs, not the engine's.
