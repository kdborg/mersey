Mersey · engine benchmarks

Plain JS, WASM polyfill, and native Mersey — compute and the web platform

The same programs written once in JavaScript and once in Mersey, run three ways in two browsers: a compute kernel that exercises the new Cranelift JIT, and six web-platform workloads — Web Storage, JSON, URL, Web Crypto, Canvas 2D, DOM — that exercise the bridge. Identical work, verified by matching checksums; the only variable is what executes the code.

Compute — where the JIT lands

A hot integer kernel (40M iterations, no allocation, no web calls) — the case the Tier-1 JIT compiles to native code. This is a different workload from the six below: those are host-bound (dominated by web-API calls); this one is compute-bound. Log scale, self-timed, lower is faster.

plain JS (JIT) native — Mersey in the fork (Cranelift JIT) polyfill — Mersey on WASM (interpreter)

Wiring Cranelift into the fork puts native Mersey within 1.4× of hand-written JS and ~150–620× ahead of the WASM polyfill, which has no JIT. On the same kernel the JIT is 65× the interpreter in the standalone engine (97 ms vs 6.3 s). The JIT does nothing for the host-bound workloads below — it refuses functions that allocate or call the host — which is why the two stories are separate.

Making native faster: two separate levers

Compute and web-platform code have different bottlenecks, so they got different work. Compute got the JIT: Cranelift is now compiled into the fork (24 vendored crates, two latent version-unification bugs in Gecko's own hashbrown/bitflags shims fixed along the way), and it delivers the 65× above. Web-platform code is host-bound — the JIT refuses it (it allocates and calls the host every iteration) — so the bridge got faster instead, in four steps: a member name crosses the ABI once as an integer (interning); scalar arguments cross without JSON (setItem(k,v), fillRect(…)); Web Storage skips JS entirely via Gecko's C++ Storage; and — most recently — strings and replies stop round-tripping through UTF-8 and JSON. The engine is UTF-32 and Gecko is UTF-16, so arguments now cross as UTF-32 (zero-copy from the engine) and replies come back typed as UTF-16 (zero-copy from nsString) — one conversion instead of three, and no reply parsing. That last step alone cut canvas 56→29, DOM 108→68, and URL 207→155 ms. The earlier interned/scalar A/B on the fork, same build, back-to-back:

How to read this honestly

  • The bridge fast paths help where the hot calls are scalars. URL (1.36×) and canvas (1.33×) gain most; JSON (0.95×, within noise) gains nothing because its argument is an object that still needs serializing. This is the win available without abandoning the universal reflective bridge.
  • Direct C++ shifts the bottleneck rather than removing it. Web Storage now bypasses JS entirely, yet it is still ~4× slower than the browser's own localStorage (which calls the same C++). Bypassing JS only bought ~1.15× over the interned bridge — because the remaining cost is no longer the crossing, it is the Tier-0 interpreter loop plus per-call string marshalling and reply parsing. Which means, for a bridge that is now fast, the JIT finally becomes the lever.
  • The JIT is done, and it is huge — for compute. Cranelift in the fork makes an arithmetic kernel 65× the interpreter and competitive with JS. It stays out of the web-platform loops by design (they allocate and call the host every iteration), so the two levers don't overlap: JIT for compute, bridge for web APIs.
  • The memory baselines differ on purpose. The polyfill pays a per-page engine tax of ~40–52 MB (WASM module + heap); the native engine adds none, because it ships inside the browser — and native's footprint is the lowest of the three.
  • Native is Firefox-only so far. The Chromium fork needs the same bridge port before it can be measured.
